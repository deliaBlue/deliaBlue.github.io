# Notes for introduction

**Neural data analysis** aims to build the path from datasets coming from
recording technologies to scientific understanding.

The evolution of new recording technologies is accompanied by neural data
analyses becoming more complex: from small, isolated code scripts with a few
dependencies to analyses routinely incorporating video-processing algorithms,
deep neural networks sophisticated graphical models and other cutting-edge
machine learning methods to create general-purpose tools applicable to many
datasets.

The necessary but largely ignored foundation of resource enabling all data
analyses: software and hardware dependencies (fig 1A). For any novel analysis,
users must spend labor and financial resources on hardware setup, software
troubleshooting, unexpected interruptions during long analysis runs, processing
constraints due to limited "on-premises" computational resources, and more.

**Major consequence** -> Reproducibility. The more dependent on complex
infrastructure stacks, the harder to work reproducibly. In machine learning,
infrastructure components dictate model performance (cite Raff, 2019).

Major efforts had been made but these still neglect key issues in the
configuration of infrastructure stacks.

Critically, management of these issues falls upon trainees who are neither
scientific rewarded nor specifically instructed on how to set up increasingly
complex core analyses and infrastructure stacks, reliant on whatever resources
are available on hand operating as a silent source of errors and inefficiency.
This reduces the accessibility of valuable analytical tools, and impedes
scientific training and progress. (cite Landhuis 2017, Merali 2010)

Neural data analysis is meant to turn recordings into scientific understanding,
which sounds tidy enough until one remembers everything required in between.

As recording technologies have advanced, so have the analyses built around them.
What used to look like a manageable script with a few dependencies can now
involve video processing pipelines, deep neural networks, graphical models, and
other methods with enough moving parts to make "just run the code" feel mildly
fictional.

The important point is that these analyses depend on more than ideas. They also
depend on infrastructure: hardware, software stacks, package versions, runtime
stability, and access to enough computational resources to finish the job before
something breaks for administrative reasons. This foundation is essential, but
easy to ignore right up until it ruins reproducibility.

And reproducibility is where the problem becomes harder to dismiss. The more an
analysis relies on a complicated infrastructure stack, the harder it is to
reproduce cleanly across users and environments {% cite raff_step_2019 %}.
**Code can be shared; the world it expects is harder to package.**

Critically, much of this burden lands on trainees. They are often left to
assemble and maintain core analysis workflows with limited instruction, limited
recognition, and whatever resources happen to be available. That arrangement is
not just inefficient. It quietly reduces access to useful tools, introduces
avoidable errors, and turns a foundational scientific problem into unpaid,
under-acknowledged technical labor {% cite landhuis_neuroscience_2017 %}
{% cite zeeya_merali_computational_2010 %}.

# Notes on middle section

NeuroCAAS: A method to precisely specify the entire infrastructure stack
underlying any core analysis and reproduce it on demand -> Makes analyses more
reproducible and accessible at scale than existing alternatives.


NeuroCAAS partitions a complete infrastructure stack into:
1. **Software level infrastructure**. All analyses are run in environments
  that are immutable due to a single script parsing input and parameters
  in a prescribed way and running the steps of the core analysis. This
  eliminates the possibility of bugs resulting from incompatible dependencies,
  mid-analysis misconfiguration or the other so-called "user degrees of
  freedom" and ensure that analyses are run within _developer-defined_ workflows.
  Currently, they have implemented 22 analyses and are actively developing more.
2. **System configuration**. Built-in job manager that automates all of the
  logistic tasks associated with analyzing data (configuring hardware, logging
  outputs, parallelizing jobs...). For each analysis
3. **Reproducible computing hardware on demand**. resource bank built on the
  public cloud, making the service globally accessible at unmatched scale.
The configuration of these three infrastructure components is concisely
summarized in a blueprint that can be automatically rebuilt.
